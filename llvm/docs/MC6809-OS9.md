# OS-9 / NitrOS-9 Module Support for LLVM-MC6809


> The system-call surface, with what is wrapped and what is tested, is in
> [MC6809-OS9-syscalls.md](MC6809-OS9-syscalls.md).  For using the compiler

> [MC6809-Toolchain-Usage.md](MC6809-Toolchain-Usage.md); for rolling one,

This is the design reference for emitting **OS-9 program modules** from
the LLVM-MC6809 toolchain (clang → llc → lld → `.os9`-style module
files), tracked under **Bug #163**.

The toolchain already produces position-independent code by default
(see [PIE design notes](./MC6809-PIE.md) if added, or the README's
"Design highlights" section), which is the structural prerequisite for
OS-9 modules — they load at arbitrary addresses with no relocation
table.

## Module file format

A program module is a single binary blob, max 64 KB.  Layout:

```
┌──────────────────────────────────────┐ offset 0
│ Sync          ($87 $CD)            2 │
│ Module size   (incl. body + CRC)   2 │
│ Name offset   (from module start)  2 │
│ Type/Language byte                 1 │
│ Attribute/Revision byte            1 │
│ Header parity (XOR of [0..8]=$FF)  1 │ ← 9-byte universal header ends
├──────────────────────────────────────┤
│ Exec offset   (program entry)      2 │ ← program-module-specific:
│ Mem size      (data area bytes)    2 │   M$Exec + M$Mem (4 bytes)
├──────────────────────────────────────┤ offset 13: body starts
│                                      │
│   Code (.text)                       │
│   Read-only data (.rodata)           │
│   Initialised-data image (.data)     │
│   Module name string (fcs-style)     │ ← optionally placed here
│                                      │   (lwlink puts it at end)
├──────────────────────────────────────┤
│ CRC trailer   (3 bytes)              │ ← bitwise complement of
└──────────────────────────────────────┘   the running CRC over body

Maximum module size: 65,535 bytes
```

**Endianness**: all multi-byte fields are big-endian.

**Header parity**: the parity byte at offset 8 is computed so that
the XOR of all 9 universal-header bytes equals `$FF`.  `lwlink/output.c:501`:

```c
buf[8] = ~(buf[0]^buf[1]^buf[2]^buf[3]^buf[4]^buf[5]^buf[6]^buf[7]) & 0xFF;
```

**CRC-24**: polynomial `0x800063`, initialised to `0xFFFFFF`, processed
byte-by-byte over the body (header + code + data + name).  The 3 CRC
bytes appended at the end are the bitwise complement of the running
state.  At validation time, processing the entire module (including the
3 CRC bytes) leaves the running state at the magic value `0x800FE3`.
Algorithm in `llvm/lib/Target/MC6809/nitros9-fmt.h::CRC::step()`.

**Type/Language byte**:
- High nibble = module type.  We emit **`Prgrm = 0x10`** for ordinary
  programs.  Other types (Sbrtn, Multi, Drivr, etc.) are out of scope.
- Low nibble = language.  `Objct = 0x01` for 6809 native, `Obj6309 =
  0x07` for HD6309 native.  Set per `-mcpu`.

**Attribute/Revision byte**:
- High nibble bits: `ReEnt` ($80, re-entrant), `ModProt` ($40,
  memory-protected — Level-2 only), `ModNat` ($20, native code).
- Low nibble = revision (0..15).  Higher revisions supersede lower in
  OS-9's module directory.
- **Recommended default for our emit: `ReEnt | ModNat = $A0`**, with
  revision starting at 0.

## Syscall interface

Mechanism: **`SWI2`** (opcode `$103F`) followed immediately by a 1-byte
function code (`FCB F$xxx` in assembly).  The kernel reads the byte
after the SWI2 instruction's PC, dispatches, returns past the FCB.

**Per-syscall conventions**:
- `A`/`B`/`D` carry small parameters (mode, size, path number).
- `X`/`Y`/`U` carry pointers (buffer, name string).
- On success: `CC.C` clear, return values in registers.
- On error: `CC.C` set, error code in `B`.

This carry-on-error idiom is critical for the picolibc runtime: every
syscall wrapper must check CC.C immediately after the SWI2 return and
translate to `errno`.

The subset picolibc needs (full enumeration in `nitros9-fmt.h::Syscall`):

| Syscall | Code | POSIX analogue | Notes |
|---------|-----:|----------------|-------|
| `F$Exit` | `$06` | `_exit()` | B = status; no return |
| `F$Mem` | `$07` | `sbrk` (heavy) | reallocates entire process block — see runtime conventions below |
| `F$Time` | `$15` | `time()` | returns Y/M/D/H/M/S in a 6-byte buffer |
| `I$Open` | `$84` | `open()` | A = mode; X = path |
| `I$Read` | `$89` | `read()` | A = path#; X = buf; Y = nbytes |
| `I$Write` | `$8A` | `write()` | A = path#; X = buf; Y = nbytes |
| `I$Close` | `$8F` | `close()` | A = path# |

**Standard path numbers match POSIX**: path 0 = stdin, 1 = stdout,
2 = stderr (inherited from the parent shell via `I$Dup` during
`F$Fork`).  Confirmed against NitrOS-9 source — e.g. `level1/cmds/build.asm`
(`lda #1` ⇒ stdout) and `level1/cmds/asm.asm:228` (`stdout=1`).  So a path
number IS the file descriptor; the picolibc syscall wrappers pass fd
straight through with **no +1 translation**.

OS-9 has **no environment variables in the Unix sense**.  `getenv()`
will return NULL.

## Program startup

When OS-9 launches a module, the entry point (`module_base + M$Exec`)
is called with these registers preloaded (from `fchain.asm:108-125`):

| Register | Contents |
|---------:|----------|
| `U` | Data area base (256-byte aligned) |
| `S` | Stack pointer: end of the data area; the stack grows toward U |
| `Y` | End of the data area (exclusive bound) |
| `X` | Start of parameter area (argv-equivalent string) |
| `D` | Parameter area size, in bytes |
| `DP` | High byte of U (so U-relative = direct-page) |
| `CC` | `Entire` set; IRQ/FIRQ masked |
| `PC` | Module entry |

Memory layout:

```
U ──►  ┌──────────────────┐
       │  .data + .bss    │
       │                  │
       │  heap (grows ↓)  │
       │                  │
       │  ⋮               │
       │                  │
       │  stack (grows ↑) │
S ──►  ├──────────────────┤
       │  parameter area  │
       │  (argv string)   │
X ──►  ├──────────────────┤
Y ──►  └──────────────────┘
```

**No `argc`/`argv` in the C sense.**  The shell builds a parameter
*string* in `[X..X+D)` — the **argument tail only; the command name is
stripped**.  The CRT tokenises it (`crt1.c`) into the `argv[]` array for
`main(int argc, char **argv)`:

- **`argv[0]`** (the program name C expects) is NOT in the parameter
  string.  Source it from the **module's own name** — the fcs-style
  name string at universal-header offset 4 — which the CRT can reach
  from its module base.
- **`argv[1..]`** come from tokenising `[X..X+D)`, NUL-terminating words
  in place (the parameter area sits in the writable process data area).
- Build the `char *argv[]` pointer array on the **stack** — it has no
  heap dependency, so it is independent of the `F$Mem` heap claim.
- `D == 0` ⇒ `argc = 1`, `argv[0]` = module name, `argv[1] = NULL`.
- The tokeniser must **leave `DP` (= `U>>8`) untouched** so direct-page
  slots keep resolving.

Quoting and separator conventions vary; the NitrOS-9 `shell` source
(`nitros9/level1/cmds/shell/`) is the reference.

## Runtime conventions

**Stack** grows downward from `S` toward `U`.  No hardware overflow
detection — programs are responsible for staying in `[U..Y)`.  The
CRT should reserve a sensible top region (suggest 256 bytes) for stack
guard space.

**Heap.**  OS-9 has no incremental sbrk; `F$Mem` sets the process's total
data-area size, and the kernel grows the area at the top.  So the start-up
code (`crt1.c`) claims once and the heap is what appears above everything
the kernel laid out:

1. `__os9_mem_request` (a linker-script knob, 16 KB by default,
   overridable with `-Wl,--defsym=`) is the total size asked for.
2. The pages granted above the old top — above the stack and the
   parameter area — become the heap, so a later `F$Mem` would extend it
   in place with nothing to move.  If the kernel refuses, or the process
   already had that much, the heap is the static pool the linker script
   carved out below the stack (`__heap_start`, `__heap_size`).
3. `sbrk` is a bump pointer over `[__os9_heap_cur, __os9_heap_end)` with
   a single `__os9_grow(bytes)` seam for asking the kernel for more.
   That seam says no today; making it live is the next heap step.

**Data area layout.**  Everything a process writes lives in its own
data area, addressed from `U`; the module body holds only code,
read-only data and the *images* of the initialised sections.  OS-9
allocates data areas in whole 256-byte pages, so `U` is page-aligned
and the kernel's `DP = U >> 8` makes the first page of the data area
the direct page.  `mc6809-os9.lds` lays the area out as U-relative
offsets (the linker-script symbols in the right-hand column):

| U + | Contents | Symbols |
|----:|----------|---------|
| `$0000` | imaginary registers `__rc0-7`, `__rs0-3` (`hi`/`lo`), `__rc8-15` — the bare-metal map, `$00-$17` | `__rc*`, `__rs*` |
| `$0018` | `.dp.data` copy: initialised `__attribute__((directpage))` objects | `__dp_start`, `__dp_data_start` |
| | `.dp.bss` (zeroed): the rest of page 0 | `__dp_bss_start`, `__dp_end` (≤ `$0100`, asserted) |
| `ALIGN(2)` | `.data` copy | `__data_start` |
| | `.bss` (zeroed) | `__bss_start` |
| | heap (`__heap_size`, default 1 KB) | `__heap_start` |
| | stack (`__stack_size`, default 512 B); `S = U + __mem_size` | `__stack_start`, `__mem_size` |

`M$Mem` is `__mem_size`.  Every OS-9 link also gets
`libclang_rt.builtins.a` from `lib/mc6809-unknown-os9/` — the integer
compiler builtins built for the os9 triple (`LLVM_BUILTIN_TARGETS`
lists both triples); the MC6839 floating-point layer is bare-metal
only until OS-9 floating point is done through the kernel's `Float09`
module.  Direct-page objects are reached by direct
addressing with the object's data-area offset as the one-byte operand
(`stb <mc6809_os9_data8(sym)`, relocation `R_MC6809_OS9_OFFSET_8`,
a link error if the object is not in page 0); other writable objects
U-relative (`ldx mc6809_os9_data(sym),u`, `R_MC6809_OS9_OFFSET_16`).
The compiler never touches `DP`, and the CRT must not either.

**Startup work.**  The kernel copies nothing and zeroes nothing, so
`crt0` copies the `.dp.data` and `.data` images from the body to
`U + __dp_data_start` / `U + __data_start`, zeroes `.dp.bss` and
`.bss`, then rebases pointers held in the copied data: a `.word sym`
in `.data`/`.dp.data` cannot be an absolute address because both the
module and the data area are placed at run time, so ld.lld writes it
as an *offset* — into the data area when `sym` lives there, else into
the module body — and lists it in the `.os9_reloc` table as
`(kind, U-relative offset of the word)`, kind 2 = add `U`, kind 1 =
add the module base, zero kind = end.  ld.lld finds the region of any
body address from the `__<region>_image_start/end` and
`__<region>_start` symbols alone, so the script is the single source
of truth for the layout.

## Good-manners checklist

A well-behaved OS-9 program:

1. **Exits via `F$Exit`, never via RTS.**  RTS would attempt to return
   through the kernel's launcher; undefined behaviour.  The CRT's
   `_exit()` calls `F$Exit` with B = exit status.

2. **Sets the right attributes.**  `ReEnt | ModNat` for ordinary user
   programs.  Re-entrancy is correct because all mutable state lives
   in the per-process data area `[U..Y)`.

3. **Picks the right language byte.**  `Obj6309 = $07` when compiled
   with `-mcpu=hd6309`; `Objct = $01` otherwise.  A 6309-native module
   set as `Objct` may load on a 6809 but produce incorrect results.

4. **Names itself sensibly.**  The fcs-style module name string should
   match the intended on-disk filename (e.g., `hello` module named
   `hello`).  The linker can derive this from the output filename.

5. **Doesn't try to fake env vars.**  OS-9 has none; `getenv()` returns
   NULL.

6. **Cleans up via F$Exit.**  `F$Exit` closes all open paths and frees
   process memory automatically — no atexit-style cleanup is required
   for OS-9 resources.

## LLVM-side integration surface

Files that will need touching:

### Object-format plumbing

- `llvm/include/llvm/TargetParser/Triple.h:332-343` — add `OS9` to
  `ObjectFormatType` enum.
- `llvm/lib/TargetParser/Triple.cpp:1194-1291` — route mc6809 ↔ OS-9
  triples (recommend a new `OSType::OS9`).
- `llvm/lib/Target/MC6809/MCTargetDesc/MC6809MCTargetDesc.cpp:80-113`
  — register a parallel `OS9Streamer` alongside `ELFStreamer`.

### MC layer

- New `llvm/lib/MC/MCOS9Streamer.cpp` + `.h` (model on `MCELFStreamer`).
- New `llvm/lib/MC/OS9ObjectWriter.cpp` — emits header + body + CRC.
- The existing relocation set (`R_MC6809_PCREL_16` et al.) does not
  change; OS-9 modules carry no external relocation table because all
  relocations are resolved by lld before module emission.

### Linker

- **Phase 2 (proof of concept)**: don't fork lld at all.  Have lld
  emit a flat binary (no ELF wrapper); a small Python tool wraps it
  with the OS-9 header + CRC.  Bypasses the largest implementation
  risk while validating the design end-to-end.
- **Phase 3**: new `lld/OS9/` directory with `Driver.cpp`,
  `Writer.cpp`, `InputFiles.cpp`.  Migrate the post-link wrapper logic
  into lld proper.

### Linker script

`compiler-rt/lib/builtins/mc6809-os9/mc6809-os9.lds` lays out the
module body (`OUTPUT_FORMAT(os9-program-module)`) and defines the
data-area layout as U-relative symbols — see
[Runtime conventions](#runtime-conventions).  `__heap_size` and
`__stack_size` are `PROVIDE`d and overridable with `-Wl,--defsym=`.

### Driver / clang

`clang/lib/Driver/ToolChains/MC6809Toolchain.{h,cpp}`:
- Recognise `-target mc6809-unknown-os9`.
- Pass `-target-format=os9` to llc/llvm-mc.
- Link against `crt0-os9.o` instead of bare-metal `crt0.o`.
- Pass the OS-9 linker script to lld.

### CRT

New `picocrt/machine/mc6809-os9/crt0.{S,c}`.  Responsibilities:
1. Capture entry registers (U, S, Y, X, D).
2. Zero `.bss`.
3. Copy `.data` from module body to `[U..)`.
4. Tokenise `[X..X+D)` → `argv[]`, `argc`.
5. Call `main(argc, argv)`.
6. Exit via `F$Exit` with the return value.

### System-call layer

`compiler-rt/lib/builtins/mc6809-os9/include/os9.h`: a system call is
one `os9 <code>` instruction, so each call is a static inline shim
whose body is a single `OS9_SYSCALL(code, (outputs), (inputs))` —
inline asm with the register traffic left to the compiler (`A`, `B`,
`d`, `x`, `y` constraints, `"c"` for the carry = failure flag, `B` for
the error code).  A new call is a few lines in the header, no assembly.

Two shapes need care:

- A call that hands back the **pair D** cannot also ask for the carry.
  Reading the carry needs a byte register, A and B are the only two, and
  the call's own result is in both; neither can be spilled, being
  physical by then.  `OS9_SYSCALL_BERR` branches over a `clrb` instead,
  so B is the error code or zero and the carry is never asked for.  Nor
  may two operands name overlapping registers — B and D together are the
  same register.
- A call that passes or returns **U** (the data-area base) is not
  expressible as inline asm at all and needs a stub that saves and
  restores it: `os9-xu.S` for the X:U pairs (I$Seek, SS.Size, SS.Pos),
  `os9-link.S` for the module calls that answer in U (F$Link, F$Load,
  F$UnLink).

Path-name calls advance X past the name they parsed, so X is an in/out
operand of I$Open, I$Create, I$Delete, I$MakDir and I$ChgDir — a shim
that calls it an input miscompiles two calls on one name.

The POSIX side is picolibc's, in `libos/os9` of that tree: read, write,
open, close, lseek, stat, fstat, ftruncate, unlink, access, mkdir, rmdir,
dirent, rename, chdir, getcwd, statvfs, sbrk, gettimeofday, isatty, getpid,
and
the OS-9-code-to-errno map.  What is not written keeps picolibc's fakes,
so those tests skip rather than fail.

### Tests

- `llvm/test/CodeGen/MC6809/` covers the module writer and the CRT
  against `tools/os9-module-check`; codegen tests carry over unchanged,
  the format being codegen-agnostic.
- `compiler-rt/test/mc6809-os9-runtime/` is the end-to-end suite: each
  case is compiled, put on a disk, run under a real NitrOS-9 boot and
  its console checked.  It covers start-up (the data images, the
  relocations, argv, the heap), the module calls and the console.  Cases
  that only mean something at one level pin it with `// LEVEL: N`.
- picolibc's own suite is the breadth: every level of it runs on both
  NitrOS-9 levels, and both are bench levels.

## Phasing

The landing strategy, with status:

| Phase | Title | Notes |
|------:|-------|-------|
| **1** | Reference doc + constants + validator | landed |
| **2** | Post-link wrapper proof-of-concept | landed: `tools/os9-link` + `mc6809-os9.lds` + `crt0.S` + 3 syscall stubs + Triple::OS9 + clang driver + `libclang_rt.os9.a` build/install + `os9.h` |
| **3** | Native lld OS-9 output | **landed**: `--oformat=os9-program-module` in lld emits a finished module directly; `tools/os9-link` is retained as a reference implementation and a byte-exact cross-checker for the lld writer |
| **4** | Full picolibc surface | **landed**: picolibc builds for `mc6809-unknown-os9` and its whole suite runs on NitrOS-9 (`libos/os9` in the picolibc tree + `scripts/run-mc6809-os9`). Console stdio, malloc, argv, time, the errno map, file I/O (open/lseek/stat/ftruncate/dirent/rename/getcwd/statvfs/mkdir/rmdir/access) |
| **5** | Polish (F$Link MC6839, Level 1 **and** Level 2) | **landed**: floating point is the MC6839 ROM linked at run time as the FPO9 module (F$Link, F$Load, F$UnLink at exit); both NitrOS-9 levels are first-class and both are bench levels |

Level 1 was not foreseen when this table was written. It is not a lesser
Level 2: a program there shares one 64K address space with the system, so
its data area does not start at zero, and that is where several classes of
mistake are visible at all — see [What the levels do not
share](#what-the-levels-do-not-share).

Where it stands: 105 of 172 tests pass at Level 1 and 258 of 342 at Level 2
(the remainder are too big for the address space, want a filesystem feature
that is not there, or are skipped by policy), and the end-to-end runtime
cases are 21/21. The system calls reached, and which of them a test would
catch breaking, are tabulated in
[MC6809-OS9-syscalls.md](MC6809-OS9-syscalls.md).

What is left is listed under [Not done, and why](#not-done-and-why).

### One-shot build path (Phase 3 onwards)

After Phase 3 the user-facing pipeline collapses to a single
clang invocation:

```sh
$ clang -target mc6809-unknown-os9 hello.c -o hello.os9
```

The driver auto-passes `--os9-name=hello` (derived from the
output stem) and, for `-mcpu=hd6309`, `--os9-type=0x17`
(Prgrm|Obj6309).  The `mc6809-os9.lds` linker script's
`OUTPUT_FORMAT(os9-program-module)` triggers the lld writer; the
script's `__mem_size = data + bss + heap + stack` symbol supplies
`M$Mem` to the writer.  The Phase 2 two-step path
(`--oformat=binary` + `tools/os9-link`) still works for anyone
who explicitly opts in.

## Building and running

picolibc builds for the target like any other cross build; what makes it OS-9
is the cross file and four options.

```sh
cd ~/GitHub/picolibc
./scripts/gen-mc6809-cross.sh                      # writes the cross files
meson setup builddir-mc6809-os9-Os \
    --cross-file scripts/cross-clang-mc6809-unknown-os9.txt \
    -Dpicocrt=false -Dsemihost=false -Dos-os9=true -Dposix-console=true \
    -Doptimization=s
ninja -C builddir-mc6809-os9-Os
```

`-Dpicocrt=false` because the C runtime comes from compiler-rt
(`libclang_rt.os9.a`: `crt0.S` places the module and claims memory, `crt1.c`
builds argv and runs the constructors); `-Dsemihost=false -Dos-os9=true`
selects `libos/os9`, the system-call layer, instead of the bare-metal
semihost one; `-Dposix-console=true` makes stdin/stdout/stderr the shell's
paths 0, 1 and 2. Floating point adds `-Dstdio-float=true -Dwant-libm=true`.

Running needs a NitrOS-9 to run on. The images live under the recipes tree,
one directory per level, and `NITROS9_LEVEL` picks which:

```sh
export PATH=$HOME/GitHub/usim:$PATH                # usim09pt
export NITROS9_RECIPES=$HOME/Documents/NitrOS-9/nitros9/recipes/picothing
PICOLIBC_BUILDDIR=$PWD/builddir-mc6809-os9-Os NITROS9_LEVEL=1 \
    python3 scripts/run-mc6809-tests --jobs 8 --include-fake-fs --opt-level os9-Os
```

`--include-fake-fs` is wanted here and not on bare metal: those tests need a
real filesystem, which is exactly what OS-9 has. A single program can be run
by hand with `scripts/run-mc6809-os9 <module>`, which formats a disk, boots,
runs it and scrapes the console.

The end-to-end cases in `compiler-rt/test/mc6809-os9-runtime/` compile a C
file, put it on a disk, boot NitrOS-9 and FileCheck the console:

```sh
MC6809_OS9_RUNTIME_TESTS=1 llvm/build/bin/llvm-lit -sv compiler-rt/test/mc6809-os9-runtime
```

They find their images the same way. Without the opt-in they report
UNSUPPORTED, so check how many ran. A case that only means something at one
level says so with `// LEVEL: N`.

Both levels are bench levels — `os9-Os` (Level 1) and `os9-Os-fp` (Level 2)
are in `bench-parallel.sh`'s default set, tallied one at a time because the
level is an environment variable. They record no cycles: a boot is most of
what a run costs, so the number would be measuring the operating system. The
size they record is the module's own, which is what has to fit.

## What the levels do not share

The system-call layer is level-agnostic; the machine underneath is not.

**The data area.** Level 2 gives a task its own address space, so `U` — the
base of everything the program owns — is 0, and a data-area *offset* and an
*address* are the same number. Level 1 shares one 64K between the program,
the system and everything else, so `U` is wherever the program was given room.
Code that confuses the two works perfectly at Level 2. `argv[0]` is the
canonical case: it is recovered from the module's own header (PC-relative
back to the module base, then the name offset the header holds) and copied
into the data area, so building it crosses from one to the other.

**Room.** A Level 2 task gets seven usable 8K blocks: a module over **57344
bytes** does not fail to load, it wedges the boot. Level 1 has no DAT at all,
shares its 64K, and says E$MemFul politely instead — which is why a third of
the suite is too big there and only a twentieth is at Level 2. The
floating-point ROM is an 8K module beside the program, which is why the FP
level is Level 2.

**Coherency.** Two paths open on one file do not see each other at Level 1. A
reader opened after a write, while the writer still holds the file, is given
the sectors the file has been allotted — sector-rounded, never written — while
the writer's bytes are still in RBF's buffer; a reader opened before the write
sees the size the file had then, and still does after the writer closes.
Level 2 reads back what was written. Write, close, then open behaves the same
at both. This is the OS, not the library: a program calling I$Create, I$Write
and I$Open directly shows it, and OS-9 has no sync call to work around it
with. Two stdio tests want the coherency POSIX promises and are recorded as a
level limitation rather than a failure.

## Not done, and why

Absent by decision, not by oversight:

- **A heap that grows.** `crt1.c` claims one with F$Mem at startup and that is
  all a program gets; `sbrk()` already routes through a `__os9_grow()` seam
  that returns failure. The design question is first: F$Mem grows the area at
  the far end, so a naive grow strands the stack and the parameter area —
  argv's strings live there — below the new top. Laying the heap above the
  stack costs a rethink of the linker script and moves nothing.
- **Processes.** No F$Fork, F$Wait or F$Chain, so no `system()`, `popen()` or
  `execve()`.
- **Signals.** No F$Send or F$Icpt, so `kill()` and `signal()` are the fakes
  picolibc supplies and their tests skip.
- **Wide characters and multibyte.** Never, as a matter of policy; those tests
  are out of scope rather than pending.
- **A link that spells itself.** The driver adds the resource-directory
  include so `#include <os9.h>` resolves, but supplies no `-lc`, no `-los9`
  and no default linker script for the OS-9 triple — a link outside meson has
  to name them all. That waits on there being a sysroot to point at.

## Validation tool usage

```sh
$ tools/os9-module-check /path/to/module.os9
/path/to/module.os9: OK (568 bytes)
  type/lang: $11 (Prgrm|Objct)
  attr/rev:  $80 (ReEnt, rev=0)
  exec offset: $00B7 (183)
  mem size:    $0224 (548)
  name: "Mdir" (at +$000D)
  CRC: valid (full CRC = $800FE3)
  tail bytes: $B7E9AF
```

The tool prints diagnostics and exits 0 on a structurally valid
module, non-zero otherwise.  Use `--quiet` to suppress the
per-module details for use in scripts.

Currently verified against:
- `compiler-rt/lib/builtins/mc6809/Float09.bin` (MC6839 FP ROM, a
  TrapLib module)
- `~/Documents/NitrOS-9/.../CMDS/mdir`, `.../CMDS/dump` (NitrOS-9
  shipping CMDS, built by lwtools)

All three produce CRC = `$800FE3`, matching the validation magic.
